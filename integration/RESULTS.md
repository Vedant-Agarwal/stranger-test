## Validation against a known, fixed bug

The same method, run against two ContextForge versions, shows a behavior present in **1.0.6** and fixed in **1.1.1**. An oauth token-exchange gateway serves a resource **template**; an uncached template instance is read over MCP (the federated path — a cached catalogued resource is served locally and never federates, so it would prove nothing). The authorization server first succeeds (control), then returns HTTP 400 for the exchange (test). A recording upstream logs each call's **header names** (not full requests) and whether an `Authorization` header was present. The inbound caller is the CF **admin** JWT (3-part, so CF's `looks_like_jwt()` guard passes and a real exchange is attempted); **untested with an ordinary, non-admin user**. Loopback only; 1.0.6 runs from the official container (`ghcr.io/ibm/mcp-context-forge:v1.0.6`), 1.1.1 is installed via pip (mcp-contextforge-gateway==1.1.1), loopback only.

| Version | exchange succeeds (control): upstream read / `Authorization` | exchange fails (HTTP 400): upstream read / `Authorization` / caller |
|---|---|---|
| **1.0.6** | True / **present** (`Bearer`) | True / **ABSENT** / content returned |
| **1.1.1** | True / **present** (`Bearer`) | False / — / **error (fails closed)** |

- **1.0.6:** the failed-exchange upstream read has the **same header names as the successful one, minus** `Authorization`. The finding is that **the gateway sends an unauthenticated request upstream** instead of failing closed. What the upstream does with it depends on the upstream: this test upstream answers without checking the token, so CF returned content; a real upstream that requires a token would refuse the request.
- **1.1.1:** when the exchange fails, **no `resources/read` reaches the upstream** and the caller gets an error (`Token exchange failed … Contact your administrator`) — the gateway **fails closed**. Deterministic across 3 test reads; the control read reached the upstream **with** `Authorization`, so the read path works and the fail result is not a harness artifact.
- **Root cause (source):** in 1.0.6 the `resource_service` token-exchange branch only logs on failure and falls through with no auth header; **1.1.1 raises `ResourceError(...)`** and fails closed. "1.1.1 fixes it" now rests on the live 1.1.1 run above, not only on reading source. **1.1.0 not tested.**
- Reproduce: 1.0.6 `integration/CONTEXTFORGE_1.0.6_GATE.md` (`integration/xid10_cf106_resource_exchange_fail.py`); 1.1.1 `integration/CONTEXTFORGE_1.1.1_GATE.md` (`integration/xid10_cf111_resource_exchange_fail.py`). Tokens redacted to `sha256:` fingerprints in the saved runs.

## agentgateway 1.7.0 (real gateway)

Official release binary v1.7.0 (git `26f5aebe99a3`), configured by file only (`backendAuth.oauthTokenExchange` on the MCP target, pointed at the local AS; inbound users validated by `jwtAuth`; no gateway-side RBAC). MCP `2026-07-28` on both sides.

**The actor is the caller, not the gateway.** agentgateway cannot obtain its own actor token; it must come from the incoming request. Here the calling agent sends a client-credentials token for `agent-client` in `x-actor-token`, so `actor_present` means the caller's actor was carried through the exchange, not that the gateway identified itself.

## Known limits

- The two-provider (same-name, different-issuer) check relies on `orig_iss`, a claim the bundled test authorization server adds to the exchanged token. Real authorization servers do not emit it, so this specific check currently exercises the probe only against the test login server, not an arbitrary production IdP.
- Each test provider (provX/provY) has its own signing key; the AS validates a subject token only with the key of its own issuer. The unregistered-issuer test runs against an AS in `--lax-subject-issuer` mode (recorded per run), so a gateway that let the token through would not be hidden by the AS refusing it.
- The clean ContextForge result covers the scenarios above on version **1.1.1 only**.
- The clean agentgateway result covers **1.7.0 only**, with the actor supplied by the caller (agentgateway has no way to mint a gateway actor token from config).
- The **1.0.6** missing-auth-on-exchange-failure catch above was observed against the official v1.0.6 container (1.0.6 is not cleanly pip-installable, so a period-correct container is required). It is a since-fixed historical behavior: the pip-installed **1.1.1** fails closed on the same test (live run above), confirming the fix.
