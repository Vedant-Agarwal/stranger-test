## Validation against a known, fixed bug

The same method, run against two ContextForge versions, shows a behavior present in **1.0.6** and fixed in **1.1.1**. An oauth token-exchange gateway serves a resource **template**; an uncached template instance is read over MCP (the federated path — a cached catalogued resource is served locally and never federates, so it would prove nothing). The authorization server first succeeds (control), then returns HTTP 400 for the exchange (test). A recording upstream logs each call's **header names** (not full requests) and whether an `Authorization` header was present. The inbound caller is the CF **admin** JWT (3-part, so CF's `looks_like_jwt()` guard passes and a real exchange is attempted); **untested with an ordinary, non-admin user**. Loopback only; 1.0.6 runs from the official container (`ghcr.io/ibm/mcp-context-forge:v1.0.6`), 1.1.1 is installed via pip (mcp-contextforge-gateway==1.1.1), loopback only.

| Version | exchange succeeds (control): upstream read / `Authorization` | exchange fails (HTTP 400): upstream read / `Authorization` / caller |
|---|---|---|
| **1.0.6** | True / **present** (`Bearer`) | True / **ABSENT** / content returned |
| **1.1.1** | True / **present** (`Bearer`) | False / — / **error (fails closed)** |

- **1.0.6:** the failed-exchange upstream read has the **same header names as the successful one, minus** `Authorization`. The finding is that **the gateway sends an unauthenticated request upstream** instead of failing closed. What the upstream does with it depends on the upstream: this test upstream answers without checking the token, so CF returned content; a real upstream that requires a token would refuse the request.
- **1.1.1:** when the exchange fails, **no `resources/read` reaches the upstream** and the caller gets an error (`Token exchange failed … Contact your administrator`) — the gateway **fails closed**. Deterministic across 3 test reads; the control read reached the upstream **with** `Authorization`, so the read path works and the fail result is not a harness artifact.
- **Root cause (source):** in 1.0.6 the `resource_service` token-exchange branch only logs on failure and falls through with no auth header; **1.1.1 raises `ResourceError(...)`** and fails closed. "1.1.1 fixes it" now rests on the live 1.1.1 run above, not only on reading source. **1.1.0 not tested.**
- Reproduce: 1.0.6 `integration/CONTEXTFORGE_1.0.6_GATE.md` (`integration/xid10_cf106_resource_exchange_fail.py`); 1.1.1 `integration/CONTEXTFORGE_1.1.1_GATE.md` (`integration/xid10_cf111_resource_exchange_fail.py`). Tokens redacted to `sha256:` fingerprints in the saved runs.

## Validation against CVE-2026-110195

[CVE-2026-110195](https://www.cve.org/CVERecord?id=CVE-2026-110195) (IBM ContextForge MCP Gateway; [advisory](https://www.ibm.com/support/pages/node/7296695); affected 1.0.0–1.0.11, fixed in **1.1.0**; reported by Nick Simpson): the RFC 8693 token-exchange cache keyed only on (gateway, user, audience) and omitted the inbound credential, so the upstream token minted for one credential of a user was served to another credential of the same user. The [`same-user-credentials` probe](../strangertest/credcache.py) **reproduces the cache-key collision described in the CVE** — it is **not a new discovery**. One user, two credentials (a session JWT and an api-token JWT); a fresh token-exchange gateway per cold run; a recording upstream ties each federated call to the credential that caused it. A cold-cache control (each credential must mint its own distinct upstream token) gates the warm test. Loopback only; tokens redacted to `sha256:` fingerprints.

| Version | cold control | warm: credential 2's upstream token | verdict |
|---|---|---|---|
| **1.0.11** | OK | **credential 1's token (reused)** | FLAGGED |
| **1.1.1** | OK | its own distinct token | OK (not vulnerable) |

- **1.0.11:** credential 2's federated call reached the upstream carrying the token minted for credential 1 (identical fingerprint): the gateway **reused a cached upstream token across two credentials of the same user.**
- **1.1.1:** credential 2's call triggered its own fresh exchange and carried its own distinct token; a cache hit on the same-credential repeat confirms the gateway still caches, so it now caches **per credential** and the collision is gone. **1.1.0** (the first fixed release) behaves like 1.1.1 here (OK (not vulnerable)).
- **Scope and privilege.** In every run both credentials carried the **same scope**, and the ContextForge caller was an **admin**, so the reproduction shows **token reuse** (credential 2 received credential 1's exact upstream token), not a privilege escalation to a scope credential 2 lacked. The probe also flags scope escalation — a distinct token carrying a scope only credential 1 holds — but that path is exercised by the practice fixtures, not these live runs.
- **Root cause (source):** `services/token_exchange_cache.py` keyed on `(gateway_id, user_email, audience)`; the fix adds the inbound `subject_token` to the key (and bumps the namespace to `v2`). Confirmed from both the version diff and the live runs above.
- **agentgateway 1.7.0 — not this class (OK (not vulnerable)).** The same probe (release binary, sha256-verified; cold cache = process restart) shows credential 2 triggering its own fresh exchange and carrying its own distinct token: agentgateway re-exchanges per credential rather than reusing a cached per-user token.
- **LiteLLM 1.109.1 — expected OK from its cache key, not run.** LiteLLM caches exchanged tokens keyed on the **subject token** (plus tenant and exchange config, per `LITELLM_GATE.md`), so two credentials of one user already get distinct entries; the probe was not run against it here.
- Reproduce: `integration/CONTEXTFORGE_SAMECRED_GATE.md` (`integration/xid10_cf_samecred_cache.py`) for ContextForge, `integration/xid10_agw_samecred_cache.py` for agentgateway. Tokens redacted to `sha256:` fingerprints in the saved runs.

## Kuadrant operator 1.6.0 (Authorino v0.28.0, mcp-controller v1.0.2)

_Kuadrant 1.6.0 Authorino token exchange (sample policy, minimally adapted) on a direct route; the mcp router/broker was not in the path._

The RFC 8693 token exchange in the Kuadrant MCP Gateway is performed by **Authorino** via an `AuthPolicy` (the gateway's broker/router does not do it). This gate drives the existing probes through an Istio Gateway whose `mcps` listener carries the sample token-exchange policy, **minimally adapted** (`integration/kuadrant/kuadrant-mcps-auth-policy.yaml`: only the issuer/token-endpoint URLs changed and Vault removed) — the mcp router/broker was **not** in the path, so this driver sets `x-mcp-servername` itself, as the router would (client-supplied values of that header are not graded or reported). Istio 1.27.0, Gateway API v1.4.1, Kuadrant 1.6.0 (Authorino v0.28.0, mcp-controller v1.0.2), local kind cluster; loopback only; see `integration/KUADRANT_GATE.md`.

| Probe | Result |
|---|---|
| delegation (A, B, A) | `actor_present` **FAIL** — Authorino sends no `actor_token`, so this is impersonation; `subject_preserved`/`audience_correct`/`scope_narrowed`/`no_token_reuse`/`no_cross_identity_bleed` all **OK** ([run](sample-runs/kuadrant-delegation.json)), each gated by an in-run thin-deputy broken fixture |
| exchange failure (token endpoint HTTP 500 / non-JSON / no `access_token` / slow) | [OK](sample-runs/kuadrant-exchange_fail.json) — nothing reached the upstream while the exchange failed; the caller got an error; the control reached it first. The user's own token reached the upstream in **none** of the modes (`user_token_reached_upstream_any_mode`=False): the gateway **fails closed** when a token that needs exchange cannot be exchanged |

- **Observation (not graded as a leak): a token already scoped to the server (`aud` = the server name) is forwarded unchanged, by design.** The exchange runs only when the inbound `aud` != the target server (`x-mcp-servername`); a token already scoped to that server skips the exchange and is forwarded as-is. This is documented — kagenti/mcp-gateway v1.0.2 `docs/design/security-architecture.md`: "The client's Authorization header is always forwarded to upstream servers ... token exchange (RFC 8693) ... as a best practice ... replacing the client's token with one of reduced scope and specific audience"; and its threat-model table lists "Client OAuth tokens forwarded to backends without token exchange — By design — all headers forwarded." The forwarded token is the holder's own, already scoped to that server, so no access is gained; see `notes/kuadrant-aud-passthrough.md`.
- The driver set `x-mcp-servername` = `svc1` as the mcp router would; client-supplied values of that header are not graded or reported.

## Known limits

- The two-provider (same-name, different-issuer) check relies on `orig_iss`, a claim the bundled test authorization server adds to the exchanged token. Real authorization servers do not emit it, so this specific check currently exercises the probe only against the test login server, not an arbitrary production IdP.
- Each test provider (provX/provY) has its own signing key; the AS validates a subject token only with the key of its own issuer. The unregistered-issuer test runs against an AS in `--lax-subject-issuer` mode (recorded per run), so a gateway that let the token through would not be hidden by the AS refusing it.
- The clean ContextForge result covers the scenarios above on version **1.1.1 only**.
- The clean agentgateway result covers **1.7.0 only**, with the actor supplied by the caller (agentgateway has no way to mint a gateway actor token from config).
- The LiteLLM result covers **1.109.1 only**, the open-source build (no JWT auth, no database), MCP 2025-11-25 (its default), one config per scenario. Its actor result depends on the login server: LiteLLM sends no actor_token.
- Whether issuer validation happens at the gateway or at the login server is a deployment choice; on LiteLLM's open-source build it happens only at the login server.
- The `act_from_client` login-server mode (an actor taken from the gateway's client authentication) is a feature of the bundled test login server; whether a production IdP does this is outside these runs.
- The **1.0.6** missing-auth-on-exchange-failure catch above was observed against the official v1.0.6 container (1.0.6 is not cleanly pip-installable, so a period-correct container is required). It is a since-fixed historical behavior: the pip-installed **1.1.1** fails closed on the same test (live run above), confirming the fix.
