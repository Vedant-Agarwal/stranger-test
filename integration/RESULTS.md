# XID-10 results

_Generated by `integration/gen_results.py` from live probe runs — do not hand-edit the tables._

Delegation-fidelity probe (XID-10: on-behalf-of / RFC 8693 token-exchange confused-deputy). Two axes of evidence: a real third-party gateway, and deliberately-broken fixtures the probe must catch. Bearer tokens are never stored; run files under `integration/runs/` keep a `sha256:` fingerprint per call. Reproduce via `integration/CONTEXTFORGE_GATE.md` and `integration/AGENTGATEWAY_GATE.md`.

## agentgateway 1.7.0 (real gateway)

Official release binary v1.7.0 (git `26f5aebe99a3`), configured by file only (`backendAuth.oauthTokenExchange` on the MCP target, pointed at the local AS; inbound users validated by `jwtAuth`; no gateway-side RBAC). MCP `2026-07-28` on both sides.

**The actor is the caller, not the gateway.** agentgateway cannot obtain its own actor token; it must come from the incoming request. Here the calling agent sends a client-credentials token for `agent-client` in `x-actor-token`, so `actor_present` means the caller's actor was carried through the exchange, not that the gateway identified itself.

| Scenario | Trigger | Verdict | Failed checks |
|---|---|---|---|
| delegation | tool | OK (not vulnerable) | — |
| impersonation | tool | FLAGGED | actor_present |
| two_issuers | tool | OK (not vulnerable) | — |
| delegation | resource | OK (not vulnerable) | — |

Detection through agentgateway itself (deliberately broken config, same gate; must be flagged):

| Fixture | What it does | Verdict | Failed checks |
|---|---|---|---|
| `broken_passthrough` | no exchange; `preserveToken` forwards the inbound user token | FLAGGED | actor_present, audience_correct |

- agentgateway caches the exchange per user (A's 1st and 3rd calls carried the same token): `True` in every row. Its cache keys on the raw subject token (plus token type, actor and extra params), not the `sub` claim.
- The caller's `x-actor-token` header reached the upstream: `False` (agentgateway strips it before forwarding).
- With the delegation config and no `x-actor-token`, agentgateway answered HTTP 400 and made no upstream call: it fails closed rather than falling back to impersonation (observed by the gate's `delegation_missing_actor` mode; no run file, since the probe cannot start).
- No vulnerability was *found* in agentgateway 1.7.0 on these scenarios. The same checks did fail on the broken config above and on the thin-deputy fixtures below.

## Known limits

- The two-provider (same-name, different-issuer) check relies on `orig_iss`, a claim the bundled test authorization server adds to the exchanged token. Real authorization servers do not emit it, so this specific check currently exercises the probe only against the test login server, not an arbitrary production IdP.
- Both test "providers" (provX/provY) share one signing key; they are distinguished only by issuer string. Real providers have separate keys — giving each its own key would be more realistic.
- The clean ContextForge result covers the scenarios above on version **1.1.1 only**.
- The clean agentgateway result covers **1.7.0 only**, with the actor supplied by the caller (agentgateway has no way to mint a gateway actor token from config).
- A comparison against the older **1.0.6** release (a since-fixed historical behavior) is future work; 1.0.6 is not cleanly pip-installable today and needs a period-correct container.
